# Agent Coordination Kit 中文设计方案与使用手册

## 1. 背景与目标

`Agent Coordination Kit` 是一个通用的多智能体协作工具，用于让多个 AI 对话框、多个角色智能体或多个开发人员在同一个 repo 的多个模块内协同工作。

它要解决的问题不是“让智能体理解代码”，而是解决协作状态的一致性：

- 当前共同目标是什么。
- 哪些任务已创建、进行中、阻塞、待 review 或已完成。
- 哪个智能体正在处理哪个任务。
- 哪些文件范围已经被 claim，避免多个智能体同时改同一片代码。
- 阻塞、决策、交接和验收证据在哪里记录。
- 新开的对话框如何在缺少上下文的情况下接手。

当前 Langflow 同步任务可以作为验证场景，但该工具本身保持通用，不绑定 Langflow、前端或后端项目。

## 2. V1 范围

V1 明确收敛为单机、单工作区协作工具：

- 支持单 repo 内多个子项目或模块。
- 支持同一共享文件系统下多个 AI 对话框协作。
- 默认一个 workspace 由一个 MCP server 管理。
- 不提供 Web UI。
- 不承诺多人多机器、跨 repo、跨工作站的强一致协作。

不在 V1 范围内：

- 分布式锁。
- 远端数据库。
- Git merge 自动解决。
- 代码 review 或测试替代。
- 复杂权限系统。

## 3. 总体架构

V1 采用三层组合：

```text
MCP server             机器一致性边界
Skill                  智能体行为规范
Markdown               人类可读视图
```

### 3.1 MCP server

MCP server 是唯一具备写入协作状态权限的组件，负责：

- agent 注册和心跳。
- task 创建、状态流转、依赖校验。
- file claim、lease、过期接管和冲突检测。
- review 权限校验。
- decision、handoff、audit log。
- Markdown 渲染。

当前实现入口：

- `team_coordinator_mcp/core.py`
- `team_coordinator_mcp/tools.py`
- `team_coordinator_mcp/server_sdk.py`

`team_coordinator_mcp/server.py` 是早期手写 stdio server，仅作为本地 fallback 保留。正式接入 Codex 时使用基于官方 Python MCP SDK 的 `server_sdk.py`。

### 3.2 Skill

Skill 只约束智能体行为，不作为安全边界。

它告诉智能体：

- 开始工作前读取上下文。
- 注册 role 和 scope。
- 改文件前 claim。
- 修改具体文件前检查 claim。
- 完成后只能推进到 review。
- 结束前必须 handoff。

当前 Skill：

```text
skills/team-agent-coordinator/SKILL.md
```

### 3.3 Markdown

Markdown 是给人读的状态视图，不是机器事实源。

生成文件：

- `AGENTS.md`
- `TASK_BOARD.md`
- `DECISIONS.md`
- `HANDOFF_LOG.md`

生成文件必须带标记：

```md
<!-- generated by Agent Coordination Kit; do not edit directly -->
```

如果目标目录中同名文件不是生成文件，渲染器会跳过，不会覆盖人工文档。

## 4. 状态模型与一致性设计

### 4.1 文件布局

初始化后，workspace 下会生成：

```text
.agent-coordinator/
├── events.jsonl
├── state.json
└── .lock
```

如果 Markdown 输出目录设置为 `.agent-coordinator/`，还会生成：

```text
.agent-coordinator/
├── AGENTS.md
├── TASK_BOARD.md
├── DECISIONS.md
└── HANDOFF_LOG.md
```

如果 `docs_dir` 指向业务目录，例如 `/home/dev/bxc/longflow_combine/plan`，则 Markdown 会输出到该目录。

### 4.2 事实源

`events.jsonl` 是唯一事实源，append-only。

`state.json` 是投影状态，用于快速读取；如果它丢失或与事件日志不一致，可通过 replay `events.jsonl` 重建。

所有纠错都通过新增事件完成，不修改历史事件。

### 4.3 写锁

所有业务写操作都会先获取：

```text
.agent-coordinator/.lock
```

锁文件内容：

```json
{
  "pid": 1234,
  "hostname": "host",
  "created_at": "2026-07-09T00:00:00Z",
  "expires_at": "2026-07-09T00:00:30Z",
  "owner": "ack-host-1234"
}
```

清理规则：

- 同 hostname 且 pid 不存在：可清理。
- 超过 `expires_at`：可清理。
- 无法判断：返回 lock conflict，不强删。

### 4.4 revision

除 `heartbeat_agent()` 外，所有写接口都支持 `expected_revision`。

规则：

- 传入 `expected_revision` 且不等于当前 revision：拒绝写入，返回最新 revision。
- 不传 `expected_revision`：MCP 在持有锁后读取最新 revision 并串行处理。

### 4.5 心跳

`heartbeat_agent(agent_id)` 是高频轻量操作，不要求 `expected_revision`。

它更新：

- agent 的 `last_heartbeat_at`。
- 该 agent 相关 active claim 的 `heartbeat_at`。

当前实现为了避免 revision 无意义膨胀，不追加心跳事件，只更新投影状态。

## 5. 核心对象

### 5.1 Agent

Agent 表示一个协作会话或智能体角色。

字段包括：

- `id`
- `role`
- `display_name`
- `scope`
- `status`
- `created_at`
- `last_heartbeat_at`

角色枚举：

```text
coordinator | frontend | backend | langflow | tester | docs | custom
```

### 5.2 Task

Task 表示可交付的工作项。

状态流转：

```text
todo -> in_progress -> review -> done
```

阻塞流转：

```text
任意非 done 状态 -> blocked
blocked -> in_progress
```

禁止：

- `todo -> review`
- `todo -> done`
- `blocked -> review`
- `done -> *`
- 通过 `update_task(..., "done")` 直接置为完成

任务完成必须走：

```text
complete_task() -> review_task(..., "approved") -> done
```

### 5.3 File Claim

File Claim 是协作锁，不是系统强制文件锁。

Claim 记录：

- `patterns`
- `expanded_paths`
- `directory_claims`
- `expires_at`
- `heartbeat_at`
- `status`

冲突检测规则：

- 对已存在文件，glob 会展开为具体路径。
- 宽泛 glob 或目录 glob 会作为目录级 claim。
- 未过期 active claim 冲突时拒绝。
- 已过期 claim 可被接管，并记录 expired 事件。

### 5.4 Decision

Decision 记录关键协作决策，例如：

- 为什么运行入口采用 `/flow/{id}?playground=1`。
- 为什么前端采用 iframe + API，而不是继续复制 Langflow 前端源码。
- 为什么某个迁移项延期。

### 5.5 Handoff

Handoff 记录交接信息：

- 本轮做了什么。
- 改了哪些文件。
- 如何验证。
- 还有哪些问题。
- 是否存在未 claim 或超出 scope 的风险。

## 6. MCP 工具说明

### 6.1 初始化

```text
init_workspace(root, docs_dir?)
```

作用：

- 初始化 `.agent-coordinator/`。
- 创建 `events.jsonl` 和 `state.json`。
- 写入 workspace 初始化事件。

示例：

```json
{
  "root": "/home/dev/bxc/longflow_combine",
  "docs_dir": "/home/dev/bxc/longflow_combine/plan",
  "goal": "Langflow 升级同步验证"
}
```

### 6.2 获取上下文

```text
get_context_bundle(role?, scope?)
```

用于新对话框接手任务。返回：

- goal
- revision
- agents
- tasks
- active_claims
- decisions
- handoffs

### 6.3 注册 Agent

```text
register_agent(role, display_name, scope, expected_revision?)
```

示例：

```json
{
  "role": "frontend",
  "display_name": "frontend-agent-01",
  "scope": ["kg-cloud-ui/apps/app-main/**"]
}
```

### 6.4 创建任务

```text
create_task(title, scope, acceptance, priority?, depends_on?, reviewer?, expected_revision?)
```

示例：

```json
{
  "title": "验证业务前端运行入口",
  "scope": ["kg-cloud-ui/apps/app-main/**"],
  "acceptance": [
    "点击运行可以打开 Langflow 运行面板",
    "不再加载旧 app-flow 微前端"
  ],
  "priority": "P0"
}
```

### 6.5 领取任务和文件范围

```text
claim_task(task_id, agent_id, file_patterns, lease_minutes?, expected_revision?)
```

示例：

```json
{
  "task_id": "task_xxx",
  "agent_id": "agent_xxx",
  "file_patterns": [
    "kg-cloud-ui/apps/app-main/src/views/agent/**",
    "kg-cloud-ui/apps/app-main/src/api/langflow/**"
  ],
  "lease_minutes": 60
}
```

如果依赖任务尚未完成，claim 可以成功，但会返回 warning；这表示可以调研，不能交付完成。

### 6.6 检查文件 claim

```text
check_file_claims(paths)
```

示例：

```json
{
  "paths": [
    "kg-cloud-ui/apps/app-main/src/views/agent/index.vue"
  ]
}
```

修改具体文件前应先调用该工具。

### 6.7 更新任务状态

```text
update_task(task_id, agent_id, status, note?, evidence?, expected_revision?)
```

常用状态：

- `in_progress`
- `blocked`

不要使用 `update_task(..., "done")`，完成必须走 review。

### 6.8 提交完成

```text
complete_task(task_id, agent_id, evidence, override_dependencies?, expected_revision?)
```

作用：

- 将任务推进到 `review`。
- 校验调用者是 task owner。
- 校验依赖任务均已 `done`。

只有 `coordinator` 可以设置 `override_dependencies=true`。

### 6.9 Review

```text
review_task(task_id, reviewer_id, result, note?, expected_revision?)
```

`result`：

- `approved`：任务变为 `done`。
- `rejected`：任务打回 `in_progress`。

权限规则：

- 有 reviewer：reviewer、tester、coordinator 可 approve。
- 无 reviewer：tester 或 coordinator 可 approve。
- owner 不能 approve 自己的任务，除非 role 是 coordinator。

### 6.10 记录决策

```text
record_decision(title, decision, rationale, impact?, supersedes?, expected_revision?)
```

建议记录：

- 架构方案选择。
- 方案放弃原因。
- 跨模块接口约定。
- 迁移边界。

### 6.11 记录交接

```text
record_handoff(agent_id, task_id, summary, changed_files, verification, open_issues, expected_revision?)
```

`changed_files` 必须是 repo root 相对路径。

如果文件不在 agent scope 或 active claim 中，MCP 会把它写入 `risks`。

### 6.12 渲染 Markdown

```text
render_markdown(expected_revision?)
```

从 `state.json` 渲染：

- `AGENTS.md`
- `TASK_BOARD.md`
- `DECISIONS.md`
- `HANDOFF_LOG.md`

注意：

- 只写固定生成文件。
- 自由文本会放入 fenced code block。
- HTML 会转义。
- 同名人工文件不会被覆盖。

## 12. 推荐协作流程

### 12.1 Coordinator 初始化

1. 启动 MCP server。
2. 调用 `init_workspace()`。
3. 调用 `register_agent(role="coordinator")`。
4. 创建任务和依赖。
5. 记录关键 decision。
6. 调用 `render_markdown()`。

### 12.2 执行 Agent 开始工作

1. `get_context_bundle(role, scope)`。
2. `register_agent()`。
3. 找到可处理任务。
4. `claim_task()`。
5. `update_task(..., "in_progress")`。
6. 开始修改文件。

### 12.3 执行 Agent 遇到阻塞

1. 判断阻塞类型：
   - 依赖未完成。
   - 接口未定。
   - 验收标准不清。
   - 文件 claim 冲突。
2. 调用 `update_task(..., "blocked", note=...)`。
3. 调用 `record_handoff()`。

### 12.4 执行 Agent 完成

1. 运行验证。
2. `complete_task(..., evidence=...)`。
3. `record_handoff()`。
4. 等待 reviewer/tester/coordinator review。

### 12.5 Reviewer 验收

1. 查看 task acceptance。
2. 查看 handoff verification。
3. 运行必要验证。
4. 通过则 `review_task(..., "approved")`。
5. 不通过则 `review_task(..., "rejected", note=...)`。

## 15. 后续演进建议

V2 可以考虑：

- 使用 SQLite 作为本地事件和投影存储。
- 提供 Web UI 或 TUI。
- 支持远端协调服务。
- 支持 Git-backed sync。
- 支持跨 repo task 关联。
- 支持更细的权限模型。
- 支持 claim 可视化和冲突推荐处理。
- 支持自动生成 reviewer 检查清单。

这些不应阻塞 V1 在单工作区内验证协作流程。
